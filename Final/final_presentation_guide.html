Final Presentation Guide

Evaluation rubric and instructions for the final project presentation and report.

Overview

The final project is assessed primarily through a written report (PDF). The evaluation emphasizes publication readiness — your work should meet approximately 70% of the requirements of a scientific paper (IMRAD structure, labeled figures, reproducible methods, honest discussion).

Deliverables (submit before or at class)

  • Final project report (PDF) — extended and improved from the midterm baseline
  • All notebooks / code (GitHub link or Kaggle notebook)

Recommended Report Organization

1) Problem Definition & Motivation

  • Background: Domain context and why this time-series problem matters.
  • Macro / societal / practical framing:
    • Macro: Economic/system-level importance.
    • Societal: Impact on people and communities.
    • Practical: How the forecast changes real operational decisions.
  • Challenge & motivation: What makes this problem hard, and why your approach is needed.

2) Data & Exploratory Analysis

  • Dataset source, size, sampling frequency, target variable, and chronological train/test split.
  • Key EDA plots: time plot, ACF/PACF, decomposition, distribution.
  • Notable patterns: trend, seasonality, outliers, missing data handling.

3) Methodology

  • Classical baseline: ARIMA/SARIMA — order selection rationale (AIC/BIC), stationarity checks.
  • ML models: Feature engineering (lags, rolling stats, calendar), model choice (RF, XGBoost), temporal validation (TimeSeriesSplit).
  • DL models (encouraged): Preprocessing pipeline (scale, window, 3D tensors), architecture (LSTM/GRU/CNN), training strategy (EarlyStopping, batch size).
  • Explain why each model was chosen — not just what you ran.

4) Results & Comparison

  • Comparison table: MAE/RMSE (or other relevant metrics) for all models side-by-side.
  • Forecast plots: Actual vs. predicted on the same test window for at least 2–3 models.
  • Analysis: Why does one model outperform another? What patterns does each capture or miss?

5) Discussion & Conclusion

  • Strengths and limitations of each approach on your specific dataset.
  • Practical recommendation: which model would you deploy and why?
  • Future work: what would improve results (more data, better features, advanced models)?

Report Structure & Title Writing Guide

Recommended Report Structure (PDF)

  • 1) Introduction: Problem context, motivation, and who benefits from the forecasting/classification output.
  • 2) Data: Dataset source, entity description, time range, features, target variable, and train/validation/test strategy.
  • 3) Proposed Method: Clearly state the main method (not only a list of tried models). Explain why it fits this task.
  • 4) Experimental Setup: Baselines, metrics, hyperparameters, and reproducibility details.
  • 5) Results & Discussion: Comparison table + plots + interpretation of errors and practical meaning.
  • 6) Conclusion: Key takeaway, deployment recommendation, limitations, and future work.

How to Write a Strong Title

Use this pattern:
<Method> + <Task> + <Objective or Dataset/Target Entity>

  • Question 1: What is the main method?
  • Question 2: What task does it serve (forecasting, classification, anomaly detection, etc.)?
  • Question 3: Who is the target entity or audience receiving value from the data (e.g., lung cancer patient, hospital, grid operator, call center manager)?

Example Title

LSTM-based Time Series Forecasting for Emergency Healthcare Call Volume Prediction in Public Hospital Systems

(Method = LSTM, Task = forecasting, Objective/Target Entity = emergency healthcare calls in public hospital systems)

Report Checklist

  • Start with a clear problem statement section.
  • Label all figures clearly: axis names, units, legends, metric definitions.
  • Show a model comparison table (not just individual results).
  • Include at least one ablation or insight (e.g., "removing lag features drops MAE by 30%").
  • Methods must be reproducible: mention hyperparameters, validation setup, random seeds.
  • Mandatory: Include a source code link in the report (GitHub / Kaggle).
  • End with takeaway bullets: what works, what fails, what is next.

Evaluation Rubric (10-Point Scale)

Your final project is graded on 5 criteria, 2 points each. Each criterion is evaluated against both course standards and publication readiness.

Criterion 1: Problem Formulation & Motivation

ScoreDescription
2.0Problem framed at macro/societal/practical levels with clear real-world relevance. Research gap or challenge explicitly stated. Reads like a paper introduction.
1.5Problem is well-motivated but missing one level of framing. Motivation present but not sharply articulated.
1.0Problem stated but purely descriptive ("we forecast X"). No connection to why it matters.
0.5Vague or missing problem statement. Dataset introduced without context.
Publication check: Could a reviewer understand why this problem matters from the introduction alone?

Criterion 2: Methodology & Technical Depth

ScoreDescription
2.0Complete pipeline: EDA → classical baseline (ARIMA/SARIMA with justified order) → at least one ML model (with feature engineering) → DL or advanced extension. Each step has clear rationale. Preprocessing justified, not just applied.
1.5Pipeline covers classical + ML but with gaps (e.g., order chosen without AIC/BIC, temporal split not explained). DL attempted but superficial.
1.0Only classical models, or ML/DL applied without proper preprocessing (random CV, no scaling). Limited justification.
0.5Single model with no pipeline structure. Significant methodological errors (data leakage, wrong evaluation).
Publication check: Is the methodology reproducible? Could someone replicate this from the description?

Criterion 3: Results, Comparison & Analysis

ScoreDescription
2.0Clear comparison table (MAE/RMSE across all models). Forecast overlay plots. Honest discussion of why one model outperforms another. At least one ablation or insight. Limitations and future work explicitly stated.
1.5Comparison table present but analysis is shallow ("XGBoost is best" without explaining why). Plots present but not well-discussed. Limitations mentioned briefly.
1.0Results reported for individual models but no structured comparison. Missing metrics or forecast plots. No discussion section.
0.5Minimal or incorrect results. No comparison across methods.
Publication check: Does the results section tell a story, or just list numbers?

Criterion 4: Report Quality & Scientific Writing

ScoreDescription
2.0Report follows clear IMRAD structure (Introduction → Data → Method → Results → Discussion → Conclusion). Figures labeled with captions, axes, legends. Tables formatted consistently. Writing is concise. Code submitted and organized. References cited where appropriate.
1.5Structure present but some sections weak (e.g., missing conclusion, unlabeled figures, inconsistent formatting). Code submitted but not well-organized.
1.0Report reads like a notebook dump — code outputs pasted without narrative. No clear section structure. Figures without labels.
0.5Report missing or extremely incomplete. No code submitted.
Publication check: If you removed the code cells, would it read like a coherent draft paper?

Criterion 5: Presentation & Communication

ScoreDescription
2.0Clear report narrative with logical flow from problem to conclusion. Writing is concise and evidence-based. Key decisions are justified. Source code link included.
1.5Most sections are present, but flow is choppy or explanations are too descriptive. Some claims are not fully supported by evidence.
1.0Report is disorganized or incomplete in key parts. Technical choices are listed but weakly justified.
0.5Missing critical sections, or report does not clearly explain methodology and findings.
Publication check: Could this report draft be submitted to a student workshop with minor revisions?
